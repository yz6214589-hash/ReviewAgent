## 1. 项目背景

### 1.1 业务背景

中国移动集团科创部每年组织重大战略研发项目院士评审。专家组需对数十个重大战略研发项目（覆盖 6G、北斗、大模型、量子计算、车路云等方向）逐一审阅项目方案、出具结构化评审意见，并填写正式打分表 Word 文档。

人工完成上述工作存在三个痛点：

1. **耗时**：每个项目需阅读数十页方案材料，逐维度撰写意见；
2. **口径不一**：不同专家/秘书撰写的意见格式、详略程度差异大；
3. **重复劳动**：同一项目往往既要写"年度总结评审"又要写"新一年立项评审"（组合评审），两份意见有大量重复结构。

### 1.2 设计注意事项

本项目在设计与开发过程中必须遵守以下注意事项，贯穿全部功能：

| 编号 | 注意事项 |
|------|----------|
| C1 | **业务规则必须配置化**：评分模板、分类关键词、范文匹配策略等业务规则不允许写死在代码中，业务调整不得要求修改代码 |
| C2 | **知识库须关联匹配**：范文参考必须与当前项目的类型/阶段/领域相关联选取，不允许使用"固定取前 N 条"式的无差别注入 |
| C3 | **无任何硬编码路径与密钥**：数据目录、模板文件路径、模型服务参数、密钥全部通过配置注入；密钥不得明文出现在代码库与界面中 |
| C4 | **入口单一、数据源一致**：只保留一个用户入口，全部功能共享同一数据通道 |
| C5 | **评审结果必须结构化存档**：每次评审的输入、识别结果、生成结果、产物文件全部入库可检索，不允许以散落文件形式存在 |
| C6 | **自动识别必须可人工干预**：任何自动识别/匹配结果在生效前都要展示给用户确认，并允许修改 |
| C7 | **交付即可部署**：提供完整依赖清单与部署文档，第三方按文档可在干净机器上独立完成部署 |

### 1.3 项目目标

| 编号 | 目标 | 衡量标准 |
|------|------|----------|
| G1 | 单项目评审意见生成 | 上传方案后 5 分钟内产出可用评审意见初稿 |
| G2 | 意见质量 | 覆盖匹配评分模板的全部维度；评审员仅需修改而非重写 |
| G3 | 组合评审支持 | 一份材料自动产出总结+立项两份意见与两份 Word 打分表 |
| G4 | 业务可配置 | 评分模板、分类规则、数据路径、模型参数不改代码即可调整 |
| G5 | 可部署可交接 | 提供完整依赖清单与部署说明，第三方可按文档独立完成部署 |

## 2. 名词定义

| 名词 | 定义 |
|------|------|
| 评审任务 | 针对一个项目方案文件发起的一次完整评审流程 |
| 项目类型 | 项目的业务分类：核心技术攻关 / 应用技术研究 / 基础研究 / 平台产品研发 / 标准体系研究 / 应用基础研究 |
| 评审阶段 | 评审所处环节：年度总结评审（对在研项目）或立项评审（对新项目），按年份区分 |
| 组合评审 | 一份项目材料中同时包含上一年度总结内容与下一年度立项内容，需分别产出两份评审意见 |
| 评分模板 | 按"项目分类 × 评审阶段"确定的评分维度与权重表，共四套（见 7.1） |
| 打分表 | 业务部门规定的正式 Word 文档，含评分维度表格与意见填写区 |
| 范文库 | 历年真实专家评审意见的结构化集合，用于指导 AI 生成意见的风格与深度 |
| 应用基础研究类 | 项目分类中的一个特殊类别，其评分模板不含"市场转化"维度 |
| 补充信息 | 评审员在生成前手工粘贴的已有专家评分、财务评审等辅助数据 |

## 3. 用户角色与使用场景

### 3.1 角色定义

| 角色 | 描述 | 核心诉求 |
|------|------|----------|
| 评审秘书（主要用户） | 科创部负责整理评审材料、起草评审意见的工作人员 | 快速产出格式规范的评审意见初稿与打分表 |
| 评审管理员 | 负责维护评分模板、分类规则、范文库、系统配置的人员 | 业务规则变化时可自助调整，不需要找开发 |
| 评审专家 | 审阅 AI 生成意见并修订（系统外角色，不直接登录系统） | 拿到结构完整、观点具体的意见初稿 |

### 3.2 典型使用场景

**场景 A：单项目立项评审（最高频）**
评审秘书收到某项目 2026 年立项申报方案（PDF，约 30 页）→ 上传 → 系统识别为"核心技术攻关类 · 2026 立项"→ 确认识别结果 → 生成评审意见 → 下载 Word 打分表 → 打印提交专家。

**场景 B：组合评审**
评审秘书收到某在研项目材料（Word），内含 2025 年总结与 2026 年目标两部分 → 上传 → 系统识别为组合评审 → 一次生成两份意见、两份 Word 打分表。

**场景 C：补充专家意见后重新生成**
评审秘书已收到部分专家的书面评分 → 在系统中粘贴补充评分数据 → 重新生成，意见中融合已有评分观点。

**场景 D：评审季批量处理**
评审季需处理 20+ 项目 → 批量上传 → 队列化逐个生成 → 全部完成后打包下载。

**场景 E：模板年度调整**
新一年评审维度权重调整 → 管理员在配置界面修改权重与维度描述 → 立即生效，无需发版。

## 5. 功能性需求

> 每条需求给出：描述、业务规则引用、验收标准。格式为 FR-编号。

### F1 项目方案上传与解析

- **FR-1.1** 支持上传以下格式的项目方案文件：PDF、Word（.docx）、Excel（.xlsx）、PowerPoint（.pptx）、纯文本（.txt/.md）。
- **FR-1.2** 系统将上传文件完整解析为纯文本，保留文档结构信息：Word 的段落与表格、PDF 的分页、Excel 的工作表与行列、PPT 的页与文本框。
- **FR-1.3** 文件大小上限可配置（默认 50MB）；超大或解析失败的文件给出明确错误提示，不中断系统。
- **FR-1.4** 上传后展示文件基本信息（文件名、大小、解析状态、解析出的文本量）。

验收标准：六种格式各用真实评审材料测试通过；损坏文件返回友好错误而非系统异常。

### F2 项目自动识别

- **FR-2.1** 上传完成后，系统基于规则自动识别以下属性（规则见 7.2）：
  - 项目类型（六类之一）
  - 技术子领域（5G/6G通信、北斗/定位、AI/大模型、云计算/算力、数据/安全、车路云、能源/低碳、芯片/硬件、机器人等）
  - 涉及年份
  - 评审阶段（年度总结 / 立项）
  - 是否组合评审
- **FR-2.2** 识别结果连同置信提示实时展示，供用户在生成前查看。
- **FR-2.3** 识别所用的关键词规则库可由管理员维护（见 F14），不写死在程序中。

验收标准：用历年真实评审材料抽样 20 个项目，类型与阶段识别准确率 ≥ 90%。

### F3 识别结果确认与人工校正

- **FR-3.1** 生成评审前，用户可对识别结果逐项人工修改：项目类型、评审阶段、子领域、是否组合评审、是否应用基础研究类。
- **FR-3.2** 人工校正结果覆盖自动识别结果，参与后续模板匹配与意见生成。
- **FR-3.3** 校正行为记录到评审任务中（谁改的、改成什么），便于复盘规则库质量。

验收标准：修改任一识别字段后，匹配的评分模板随之实时更新展示。

### F4 评分模板自动匹配

- **FR-4.1** 系统根据"是否应用基础研究类 × 评审阶段"自动匹配四套评分模板之一（规则见 7.1）。
- **FR-4.2** 匹配结果（模板名称、各维度名称/权重/说明、总分）在生成前向用户完整展示。
- **FR-4.3** 模板内容由管理员可配置（见 F14），配置变更即时生效。

验收标准：四套模板各匹配一次，维度权重展示与配置一致。

### F5 补充信息录入

- **FR-5.1** 用户可在生成前粘贴两类补充信息（均为选填）：已有专家评分数据、财务评审数据。
- **FR-5.2** 补充信息作为上下文参与 AI 评审意见生成。
- **FR-5.3** 补充信息随评审任务存档，可在历史记录中查看。

### F6 AI 评审意见生成

- **FR-6.1** 用户确认识别与模板后，一键触发评审意见生成。
- **FR-6.2** 生成内容必须覆盖匹配模板的**每一个维度**：逐维度评述 + 综合评价 + 分维度评分建议（区间）+ 总分建议（区间）。
- **FR-6.3** 生成过程对用户可见：展示当前处理步骤与进度；评审文本流式逐步呈现。
- **FR-6.4** 生成时自动从范文库选取与当前项目相关的往期真实评审意见作为风格参考（关联规则见 F12）。
- **FR-6.5** 生成失败的错误信息明确可读（如"模型服务不可达"），支持重试，重试不丢失已确认的分类结果与补充信息。
- **FR-6.6** 生成完成后用户可对文本进行编辑修改，再进入输出环节。

验收标准：生成意见覆盖模板全部维度；中断重试后无需重新上传文件。

### F7 组合评审双份输出

- **FR-7.1** 当识别（或人工指定）为组合评审时，系统自动将材料内容按阶段拆分（规则见 7.3）。
- **FR-7.2** 分别按两套评分模板生成两份独立评审意见：年度总结评审意见、立项评审意见。
- **FR-7.3** 两份意见在界面上分区展示，各自独立生成 Word 打分表。

验收标准：用真实组合材料测试，产出两份意见且各自维度与其对应模板一致。

### F8 Word 打分表生成与下载

- **FR-8.1** 系统基于业务部门规定的空白打分表模板，将评审意见填入生成正式 Word 文档。
- **FR-8.2** 填充内容包括：项目名称、评审组名、日期、打分表意见栏（总结意见填左栏、立项意见填右栏，规则见 7.4）、完整评审意见详情附录。
- **FR-8.3** 空白模板文件可配置更换；模板缺失时系统使用内置的通用排版生成 Word，并明确提示当前为备用格式。
- **FR-8.4** 界面提供下载按钮；文件同时存档（见 F10）。

验收标准：产出的 Word 在 Microsoft Office 中正常打开，格式与正式打分表一致，合并单元格内容完整。

### F9 Markdown 评审意见导出

- **FR-9.1** 评审意见可导出为 Markdown 文件下载与存档。

### F10 评审历史记录管理

- **FR-10.1** 每次评审任务自动存档：上传文件名、识别结果（含人工校正）、补充信息、生成的意见全文、产出的文件、操作人、时间。
- **FR-10.2** 提供历史列表：按时间/项目名/类型/阶段检索。
- **FR-10.3** 历史记录中可重新下载产物、查看详情、基于同一项目"再次生成"（新建任务并复用上次的校正结果与补充信息）。

### F11 批量评审（P2）

- **FR-11.1** 支持一次上传多个项目文件，形成评审队列逐个处理。
- **FR-11.2** 队列中每个任务独立展示状态（待处理/识别完成待确认/生成中/完成/失败）。
- **FR-11.3** 全部完成后支持打包下载全部产物。

### F12 范文库管理与关联匹配

- **FR-12.1** 范文库以结构化形式存储往期真实评审意见，每条范文包含：项目名称、项目类型、评审阶段、意见分区、专家姓名（可脱敏）、意见原文。
- **FR-12.2** 管理员可对范文进行新增、编辑、删除、导入（支持从既有 JSON 格式范文数据批量导入）。
- **FR-12.3** 生成评审时，按"项目类型 + 评审阶段 + 技术子领域"从范文库中匹配最相关的 K 条意见注入生成上下文（K 可配置，默认 6 条，来自 ≥2 个不同项目）。
- **FR-12.4** 无匹配范文时正常生成，并在界面提示"本次未使用范文参考"。

### F13 评审标准说明展示

- **FR-13.1** 系统内置"评审标准说明"页，完整展示四套评分模板的维度、权重、说明与适用场景，以及项目类型识别规则说明。
- **FR-13.2** 说明页内容跟随 F14 的配置自动更新。

### F14 业务规则与系统配置管理

- **FR-14.1** 以下业务规则以配置形式管理，管理员可在界面或配置文件中修改，无需改代码、无需重启：
  - 四套评分模板（维度名、权重、说明）
  - 项目类型/阶段/子领域的识别关键词规则
  - 范文匹配条数 K
- **FR-14.2** 以下系统参数以配置形式管理：
  - 模型服务地址、模型名称、密钥（密钥不明文落盘展示）
  - 数据存储目录、Word 空白模板文件路径
  - 文件大小上限、文本截取长度等处理参数
- **FR-14.3** 配置修改留痕（修改时间、修改人、旧值/新值）。

### F15 历史评分数据导入（P2）

- **FR-15.1** 支持导入既有专家评分文档（Word 打分表、意见反馈表），解析为结构化评分数据。
- **FR-15.2** 导入的评分数据可作为对应项目评审任务的补充信息自动关联。

## 6. 数据需求

### 6.1 核心数据实体

| 实体 | 关键字段 | 说明 |
|------|----------|------|
| 评审任务 | 任务ID、文件名、原文内容、识别结果、人工校正结果、补充评分、补充财务、状态、创建人/时间 | 一次评审的完整上下文 |

| 识别规则 | 规则类型（类型/阶段/子领域）、关键词列表 | 驱动自动识别 |
| 配置项 | 配置键、值、修改记录 | 系统与业务配置 |
| 操作日志 | 操作人、操作类型、对象、时间、变更内容 | 审计留痕 |

### 6.2 输入数据

- 项目方案文件：六种格式（见 F1）
- 补充信息：自由文本
- 历史评分文档：Word（打分表/意见反馈表/财务意见表三种版式，P2）
- 范文初始化数据：历年真实评审意见（JSON，约 78 个项目）

### 6.3 输出数据

- Word 打分表：命名 `评审报告_<项目名>[_<阶段>].docx`
- Markdown 意见：命名 `评审意见_<项目名>.md`
- 批量评审打包文件：ZIP

## 7. 业务规则

### 7.1 评分模板体系（BR-1）

评分模板 = f（是否应用基础研究类， 评审阶段），共四套，总分均 100：

| 分类 | 阶段 | 维度与权重 |
|------|------|-----------|
| 非应用基础研究类（默认） | 年度总结 | 目标完成度30 + 成果丰富度10 + 技术水平先进性20 + 科技成果影响力10 + 市场转化30 |
| 非应用基础研究类 | 立项/目标 | 战略性20 + 先进性20 + 体系化20 + 可行性10 + 市场转化30 |
| 应用基础研究类 | 年度总结 | 目标完成度40 + 成果丰富度20 + 技术水平先进性30 + 科技成果影响力10 |
| 应用基础研究类 | 立项/目标 | 战略性30 + 先进性30 + 体系化30 + 可行性10 |

规则要点：

- 应用基础研究类**不含市场转化维度**；
- 项目类型无法识别时默认按"非应用基础研究类"处理；
- 各维度附带说明文字，作为评分模板初始配置的一部分随系统交付，示例：目标完成度="项目目标达成情况、指标完成度、跳高指标表现"；市场转化="行业核心需求满足、竞品对标、收入转化"；战略性="国家战略、产业升级、企业经营发展匹配度"。

### 7.2 项目自动识别规则（BR-2）

- **类型识别**：基于关键词命中计数，命中最多的类型胜出，零命中默认"核心技术攻关"。初始关键词组：
  - 核心技术攻关：核心技术、关键技术、技术攻关、能力攻关、核心技术研究、核心能力、技术突破、关键技术攻关
  - 应用技术研究：应用技术、应用研究、应用攻关、技术应用、应用验证、示范应用、应用示范、技术转化
  - 基础研究：基础研究、前沿技术、基础理论、原始创新、探索研究、前沿研究
  - 平台/产品研发：平台研发、产品研发、系统开发、平台开发、平台建设、系统研发、原型研制
  - 标准/体系研究：标准化、标准制定、体系研究、体系构建、评测体系、标准体系、规范研究
  - 应用基础研究：应用基础、基础应用、应用基础研究、前沿基础、应用基础类
- **年份识别**：提取文中 2024–2029 年份，取最早出现者，无则默认当前评审年。
- **阶段识别**：按"XX年总结/成果/完成"判定总结阶段；按"XX年目标/计划/立项/指标"判定立项阶段。
- **子领域识别**：按关键词组归入 5G/6G通信、北斗/定位、AI/大模型、云计算/算力、数据/安全、车路云、能源/低碳、芯片/硬件、机器人等领域，可多命中时取计数最高者。
- 识别范围 = 文件名 + 正文前若干字符（默认前 8000 字符，可配置）。

### 7.3 组合评审判定与内容拆分（BR-3）

- 同一份材料同时命中"总结类阶段"与"立项类阶段"关键词 → 判定为组合评审。
- 内容拆分：按阶段关键词出现的行位置作为边界，将正文切分为各阶段内容块；无法定位边界的阶段回退使用全文。

### 7.4 Word 打分表填充规则（BR-4）

- 使用业务部门提供的空白打分表文件作为底稿。
- 打分表意见行为合并单元格：**左栏填年度总结意见，右栏填立项/目标意见**；组合评审时按阶段各出一份。
- 各维度意见以"√ 维度名=权重分意见：xxx"格式合并填入对应栏。
- 表格外追加完整评审意见全文作为详情附录。
- 项目名称、评审组名、日期自动填入指定位置。

### 7.5 评审意见内容规范（BR-5）

AI 生成的评审意见须满足：
1. 覆盖匹配模板的每个维度，逐维度评述；
2. 每个维度给出评分建议区间，并给出总分建议区间；
3. 指出不足时必须给出具体问题与改进建议，不说空话；
4. 引用方案中的具体数据/指标作为支撑；
5. 语言专业简洁，风格对齐范文库中的真实专家意见。

## 8. 非功能性需求

| 编号 | 类别 | 需求 |
|------|------|------|
| NFR-1 | 部署 | 提供完整依赖清单与部署文档；第三方按文档可在干净机器上独立完成部署；无硬编码本机路径 |
| NFR-2 | 性能 | 单项目评审（含生成）端到端 ≤ 5 分钟；文件解析 ≤ 10 秒；界面操作响应 ≤ 1 秒 |
| NFR-3 | 可用性 | 模型服务不可达时，除 AI 生成外的功能（上传、识别、模板查看、历史查阅）全部可用 |
| NFR-4 | 安全 | 密钥等敏感配置不明文出现在代码库与界面中；系统部署于内网，不依赖公网服务 |
| NFR-5 | 可靠性 | 生成中断可重试且不丢失任务上下文；所有产物落盘存档 |
| NFR-6 | 可维护性 | 业务规则（模板/关键词/范文）全部配置化；代码有分层结构与说明文档 |
| NFR-7 | 数据合规 | 评审材料属内部敏感资料，数据不出内网；范文库支持专家姓名脱敏 |

## 9. 边界：本版不做的事

1. 不做评审专家在线协同打分（专家仍是线下评审，系统服务秘书起草环节）；
2. 不做评分自动汇总计算（专家打分数据的自动聚合分析属 P2 之后）；
3. 不做用户权限分级体系（v1.0 单租户内网使用，管理员/秘书通过简单口令区分即可）；
4. 不做移动端。

## 11. 验收标准汇总

v1.0 交付时须通过以下场景验收：

1. 场景 A（单项目立项）：用真实立项材料完成全流程，产出规范 Word；
2. 场景 B（组合评审）：用真实组合材料产出双份意见与双份 Word；
3. 场景 C（补充信息）：粘贴评分后重新生成，意见体现补充内容；
4. 场景 E（模板调整）：管理员修改权重后新任务立即使用新模板；
5. 识别准确率：20 个真实项目抽样，类型+阶段准确率 ≥ 90%；校正功能可用；
6. 部署验收：在干净机器上按部署文档独立完成部署并跑通场景 A；
7. 降级验收：断开模型服务，系统其余功能可用且提示明确。
